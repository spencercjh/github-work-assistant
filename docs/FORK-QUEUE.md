# 持续准备同步 PR

PR 队列适用于 `adapted-batches`：前一批通过验证、只等待审阅时，执行者可以继续准备后续批次。每批独立保存来源、依赖、PR 和验证证明，仍按来源顺序合入配置的集成分支。默认关闭队列；原始上游提交的原样同步继续采用串行流程。

队列只增加待审改动的准备能力。自动合并、部署、镜像发布和跨仓库写入继续使用各自的授权，开启队列不增加这些权限。服务采集和校验状态，原维护执行者负责适配、签名、远端写入和重建；服务本身不执行 GitHub 写操作。

## 配置

在已授权的 fork 规则中增加 `queue`。下面只是配置示例，不会创建分支或修改仓库：

```json
{
  "id": "product-next",
  "upstream": {"repo": "example/community", "branch": "main"},
  "target": {"repo": "example/product", "branch": "next-release-dev"},
  "local_repository": "/srv/product-clone",
  "queue": {"max_open_prs": 10}
}
```

`queue` 缺省或为 `null` 时保持串行模式。存在该对象时启用队列，`max_open_prs` 可设为 1–50，省略或设为 0 时取 10。上限计入所有未完成批次，包括尚未开 PR 的准备批次；它不是构建并发数。同一维护对象一次只运行一个受控验证，不在测试期间切换批次。

目标仓库仍需 `local-edit`、`fork_sync_mode: "adapted-batches"` 和可信测试命令。持续授权的 `github_actions` 应分别列出所需动作：

- `push`、`open-pr`：推送本批同步分支并创建 PR。
- `edit-pr`：修改标题和正文，保留测试生成的来源表。
- `retarget-pr`：重建后切换原 PR 的目标分支，只允许检查返回的 `base` 字段。
- `merge`：单独授予的合入权限。未授予时，仍可准备多个 PR，等待人工合入。

先完成已发布的串行批次，再启用队列。修改队列策略会改变指引版本，尚未完成的证明需要重新核验。关闭队列前先完成全部批次；存在未完成批次时，采集入口拒绝继续，恢复配置后可接续。全部完成后关闭会归档批次记录并恢复串行模式。

## 批次和合入顺序

| 批次 | 提前审阅时的 PR 目标 | 允许实际合入的目标 |
| --- | --- | --- |
| A | `next-release-dev` | `next-release-dev` |
| B | A 的同步分支 | A 合入后，重建并切换到 `next-release-dev` |
| C | B 的同步分支 | A、B 合入后，重建并切换到 `next-release-dev` |

B → A、C → B 只用于展示各批差异，不能实际合入这些分支。合入检查要求当前批次是第一个未完成批次，已脱离前序同步分支，PR 的真实目标为正式集成分支。人工越序合入也不会推进本地同步位置，需要另行核对已发布历史。

准备流程沿用[适配批次](FORK-MAINTENANCE.md#分批适配有较多定制的仓库)的来源清单、工作区和完整测试要求：

1. 刷新上下文、确认原维护归属并关联当前证据。
2. 首次调用 `start-sync-batch --after <已确认的上游起点> --count <批量大小> --reason-file <说明>`；后续省略 `--after`。
3. 按 `batch_commits` 适配、签名并填写来源映射，运行 `test-worktree`。
4. 通过对应 `check-github-action` 后推送并创建 PR，核对远端 head、目标和来源正文。
5. 记录 `changes-ready`。前序均通过受控验证、公开为当前提交的 PR、没有已观察到的失败检查且只等审阅时，继续 `start-sync-batch`，直到达到上限或没有新来源。

若剩余问题仅为人工审阅或合并选择，先按原流程向决策者提问，再用 `record-work-result --outcome needs-decision --review-only`。它保留决策报告，同时将该批记为等待审阅；证明、已发布 PR、目标和检查仍必须满足 `changes-ready` 条件。冲突、正确性问题、测试失败不能标为 `review-only`，使用普通 `needs-decision` 阻断依赖链。远端 CI 的必要检查和最终合入条件仍由仓库指引决定；未观察到失败不等于全部远端 CI 已通过。

队列沿用一个维护对象及其原负责人，不为各 PR 新建维护对象。`fork` 是当前选中批次，`fork.queue.batches` 保存全部活跃批次。需处理前序 PR 的评论或失败时，先选中它：

```bash
"$INSTANCE/run" select-sync-batch "${work[@]}" --batch "$BATCH_ID"
```

选批会产生新证据。重新读取并关联当前事件后再运行工作区、测试或写入检查；旧事件不能修改另一个批次。

在原批次中修复评审问题时，更新来源映射并重新运行 `test-worktree`。验证会固定当时的远端 head，允许通过检查后推送新的已测提交；未推送的提交不能记为 `changes-ready`。这不授予强制覆盖权限：非快进更新仍需准确的分支替换授权或重建租约。远端出现非预期修改时，先核对变化。

## 前序变化和重建

采集器读取所有活跃 PR。前序 head 变化、Squash 合入、集成分支新增补丁、人工修改 PR 目标等情况会使受影响批次标记 `queue_stale`。旧证明保留供审计，但不能再用于推送或合入。后续工作不因自己的 head 未变而获得豁免。

按从旧到新的顺序处理：

1. 完成前序合入结果的核验登记；若前序仍有错误，先修复并验证前序。
2. 选中需要重建的批次，刷新关联后调用 `rebuild-sync-batch "${work[@]}" --batch "$BATCH_ID"`。
3. 返回值保留相同 `batch_id`、`batch_after` 和 `batch_commits`，生成新的 `round`，清除可用证明。使用 `rebuild_source_head`、`rebuild_from_base` 及旧工作区核对需要重放的适配。
4. 运行 `prepare-worktree`。新一代使用独立本地分支，返回的 `local_branch` 与远端 `branch` 可能不同。原工作区及未提交内容不被重置。执行者按来源顺序重放适配、保留上游作者、重新签名、重建映射并完整测试。
5. 对仍打开的原 PR，`check-github-action --action push` 只允许替换重建时捕获的准确远端 head。检查返回 `expected_remote_head` 时使用显式 `--force-with-lease=refs/heads/<branch>:<expected_remote_head>`；远端再次变化必须重新核对，禁止无条件强推。
6. 需要切换目标时，使用 `--action retarget-pr --ref <同步分支> --head <新head> --base <新受测目标SHA> --pr-base <PR当前报告的base SHA>`。只有 `permitted=true` 且 `editable_fields=["base"]` 才能切换到返回的 `target_branch`。单独的 `edit-pr` 检查不允许切换目标。
7. 核对远端结果、刷新正文中的来源表、等待必要 CI，并对新的 head 与目标重新审阅。旧批准不因 PR 编号相同而继续有效。合入仍只操作队首，使用正常 Squash 及准确 head，不绕过仓库保护。

重新验证之后，按队列状态继续处理受影响后序。无需重复启动正在运行的验证。服务重启保留批次、依赖和验证尝试；过期测试心跳仍按现有恢复规则处理。

## 异常恢复

| 情况 | 处理 |
| --- | --- |
| PR 创建成功，客户端没收到响应或本地未登记 | 用已保存的确定性同步分支查找原 PR，采集恢复编号；不再创建一个 PR。 |
| 已知 PR 未出现在查询结果中 | 返回错误，保留原记录；不推断 PR 已删除。 |
| 人工关闭但未合入 | 暂停该链。核对关闭原因后，明确重建同一批次；新分支重试相同来源范围，旧 PR 留作历史。即使旧分支已删除，仍可采集其后序 PR；后序须重建到新分支后才能继续。 |
| 人工修改 head 或目标 | 标记失效，原负责人先核对编辑内容，再选择修复或重建；不复用旧证明。 |
| 前序测试或 CI 失败 | 后序操作被拒绝；先修复前序，不能用切换批次绕过。 |
| 同一提交的 CI 状态重试成功 | 刷新证据。提交状态按不区分大小写的 `context` 取最新记录；旧失败留作历史，不继续阻断。其他状态或检查运行的失败仍会阻断。 |
| 队首已经合入，登记前重测覆盖了原证明 | 按[历史证明恢复](FORK-MAINTENANCE.md#恢复被后续测试覆盖的合入前证明)核验部署者固定的原始证明。恢复成功只解除该队首的失效标记；后序仍须重建，同步位置仍由正常合入结果登记推进。 |
| 人工越序合入或合到同步分支 | 不推进已合入位置，也不把已合入历史当作可重建工作区；交由人工核对恢复。 |
| 集成分支改写历史，丢失已登记的合入提交 | 拒绝继续准备、重建或写入；先人工核对实际历史与同步位置。旧批次移出活跃窗口后，此检查仍然有效。 |
| 多个执行者同时选批、续批或保存证明 | 版本检查拒绝迟到写入，刷新后由实时负责人继续。 |

重建或移出活跃窗口时，旧代的证明、来源和远端证据摘要随事务一起归档。讨论正文仍按现有事件保留策略处理。归档记录不能直接充当当前通过证明；已合入队首的历史证明恢复必须另行核验原始文件、日志、来源映射和实际合入历史，并保留最后一次真实测试的结果。

## 进度和耗时

`queue.prepared_through` 表示已经准备并发布到哪里的来源范围，历史上达到该位置不保证旧代仍然有效；同时检查每批的 `queue_stale`。`queue.merged_through` 与成功同步位置只在真实合入的父提交、文件树和来源核验通过后推进。

`status` 的 `fork_queue_metrics` 给出未完成批数、最老未完成批次的年龄，以及每批当前代的准备耗时、最后一次验证耗时和等待审阅耗时，单位为秒。准备耗时是从创建或重建到测试开始的墙钟时间，可能包含执行者暂停；它不是 CPU 时间。比较实际已合入的上游位置和等待时间，不能用 PR 数替代同步完成度。

## 企业版分支流程

仓库负责人从已验收的企业版提交建立 `next-release-dev`，记录对应上游基线后再配置同步。企业版主线新增修复由该负责人通过独立 PR 纳入集成分支；PR 记录原提交或补丁编号，先检查是否已包含，冲突交给该修复及同步负责人共同处理。集成分支变化会使待审队列重建和重验。

进入发布窗口时，负责人固定集成提交、上游位置和企业版补丁集合，通过独立发布 PR 回到既有验收流程。第一版只维护一条线性上游队列，不自动做企业版两条分支的双向同步，也不自动跳过被拒绝的批次。

串联 PR 的 CI 过滤要覆盖实际 PR 目标，包括同步分支。逐个检查验证工作流是否需要增加 `next-release-dev` 或 `ghraft/sync/**`；发布工作流的触发条件、凭据和分支保护分别核对，不整体扩大。先在获准的测试仓库验证创建、失效、Squash、重建与恢复流程，再启用实际维护规则。
